# Привязка расхода к медиа-элементу Daminion

Что нужно в шлюзе, чтобы расход можно было разложить по медиа-элементам, каталогам и типам медиа.

Короткий ответ: **почти ничего.** Нужна одна правка в разборе `X-METADATA`; всё остальное уже есть.

## Что считает шлюз, а что Daminion

Стоимость целиком остаётся здесь. Daminion её не получает, не хранит и не пересчитывает — в новом
сервере он показывает только общий баланс через `/api/credits`. Раньше рассматривался вариант с
возвратом стоимости запроса в заголовке; он отменён.

Это заодно снимает три проблемы, которые тот вариант тянул за собой: шкала кредитов не аддитивна
(`Σ spent(xᵢ) ≠ spent(Σxᵢ)`), из суммы не восстановить доллары, а расход элемента, не дошедшего до
конца из-за падения процесса, терялся бы вместе с памятью процесса.

## Что шлёт CVis

На каждый запрос к провайдеру — включая каждый кадр видео и каждый кусок аудио одного элемента:

```
X-CUSTOM-EVENT-ID: <id медиа-элемента>:<guid медиа-элемента>
X-METADATA:        {"catalog":"<имя каталога>","mediaType":"photo|video|audio"}
```

**Почему id и guid вместе.** Id уникален только внутри каталога, а события можно запрашивать по
одному customId без ключа (`storage/postgresql/event.go:366` требует лишь один из трёх фильтров) —
«Photos, id=1» совпало бы у разных клиентов. Guid даёт уникальность, id рядом с ним позволяет
сверить событие с каталогом, не заглядывая в базу.

**Почему тип медиа приходит от CVis, а не выводится здесь.** По событию его не восстановить: кадры
видео уходят тем же `/v1/chat/completions`, что и фото. Отличить их может только отправитель, и
только в момент запроса.

## Что уже готово и править не нужно

| Что | Где |
|---|---|
| Чтение `X-CUSTOM-EVENT-ID` | `internal/server/web/proxy/middleware.go:215` |
| Запись в событие | там же, `:288` (`CustomId`) |
| Колонка `events.custom_id VARCHAR(255)` | `internal/storage/postgresql/event.go:44` |
| Индекс по ней | `event.go:135`, `idx_events_custom_id` |
| Фильтр в API событий | `event.go:365-378`, `GetEvents(userId, customId, keyIds, start, end)` |
| Перечисление customId по ключу | `event.go:494` |
| Колонка `events.metadata JSONB` | `event.go:44` |
| Стоимость запроса в событии | `events.cost_in_usd` |

Новую колонку заводить не нужно: `custom_id` есть в схеме, проиндексирована и доступна фильтром.

## Единственная нужная правка: `X-METADATA` сохраняется строкой, а не объектом

`internal/server/web/proxy/middleware.go:236-244`:

```go
if len(metadata) != 0 {
    data, err := json.Marshal(metadata)   // metadata — это string
    ...
    metadataBytes = data
}
```

`metadata` получен из `c.Request.Header.Get("X-METADATA")`, то есть это `string`. `json.Marshal`
от строки даёт **строковый литерал JSON**, а не объект: в `events.metadata` (JSONB) окажется

```json
"{\"catalog\":\"Photos\",\"mediaType\":\"video\"}"
```

— скаляр-строка, а не документ. Из-за этого `metadata->>'catalog'` не работает, и группировка по
каталогу или типу медиа средствами SQL невозможна: сначала пришлось бы доставать строку через
`metadata #>> '{}'` и разбирать её второй раз.

Правка на одну строку — сохранять тело как есть, если это валидный JSON:

```go
if len(metadata) != 0 {
    if json.Valid([]byte(metadata)) {
        metadataBytes = []byte(metadata)
    } else {
        telemetry.Incr("bricksllm.proxy.get_middleware.invalid_metadata", nil, 1)
    }
}
```

Оговорка: если кто-то уже полагается на нынешнее поведение и шлёт в `X-METADATA` произвольный
текст, после правки такой текст перестанет сохраняться (он не валидный JSON) — вместо молчаливого
оборачивания в строку будет счётчик в телеметрии. Стоит проверить, нет ли таких отправителей,
прежде чем менять.

## Что можно посчитать после этого

```sql
-- расход по одному медиа-элементу
select sum(cost_in_usd) from events where custom_id = '12345:0f1e...';

-- по типам медиа за период
select metadata->>'mediaType' as kind, sum(cost_in_usd), count(*)
  from events
 where key_id = $1 and created_at between $2 and $3
 group by 1;

-- самые дорогие элементы каталога
select custom_id, sum(cost_in_usd) as usd
  from events
 where metadata->>'catalog' = 'Photos'
 group by 1 order by usd desc limit 20;
```

Последние два запроса и есть то, ради чего нужна правка выше: без неё `metadata->>'…'` вернёт
`null`.
